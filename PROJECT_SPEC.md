# Jules Berne’s Pie Chart — Project Specification

**Status:** Agreed product requirements, with implementation status noted separately below.  
**Current prototype:** v0.1.055  
**Project/package name:** `PieChart`

## 1. Purpose and approach

A free, phone-first personal nutrition, activity, and weight tracker, designed primarily for everyday use by one person, with a second user able to test and maintain it. It replaces the practical tracking functions of Noom, not its coaching or educational content. Everyday recording should be quick; the app should not require routine database administration.

Develop the web app on GitHub Pages first, then provide Android integration where browser capabilities are insufficient. Keep the interface lean, touch-first, and consistent with the existing approved design. Do not introduce dashboards, controls, or complexity without a clear need.

## 2. Home screen and charts

**The home screen is the graph**, with a compact title bar featuring the approved right-facing meat-pie slice on a nautical chart, the name **Jules Berne’s Pie Chart**, and settings. The installed-app icon uses the same artwork. Enlarge the title, logo, and settings control to use available room **within the existing title-bar height**, without reducing graph space. The Fats metric uses a visibly fatty/oily icon, distinct from Water.

Eight independent, vertically stacked chart bands appear by default, in this order: **Weight, Steps, Water, Calories, Fibre, Protein, Fats, Carbs**. Each has its own native-unit vertical scale, a distinct existing colour, fine daily marks with short downward fades, and thin full-width separators. The integrated right-hand label column shows the metric, actual reading, applicable target/budget, and a prominent percentage when a valid target exists. The far-right, 12 px colour strip has a muted full-height background and a saturated fill proportional to target achievement. Do **not** invent fat or carbohydrate targets. The large Fats and Carbs right-hand readouts show **whole grams (rounded to the nearest gram), with no space before `g`** in both signed-in and sample views; underlying stored quantities and food-edit nutritional precision remain unchanged. Weight percentage represents actual weight divided by target weight, not weight-loss progress.

When signed into an authorised Firebase account, each graph metric uses **its own first real recording as the handover from sample history to personal data**: weight, water, steps, and food-derived nutrition are independent. Exercise entries affect the Steps band's activity markers, not the sample-history cutoffs for unrelated metrics. Before each metric's own first actual record, bundled CSV history may be shown; real values always take priority. No sample data may override a recorded value. The CSV is a public GitHub Pages file, and its historical data is visible to both members; it is not private, per-account history. When signed out, the sample chart remains available as a labelled prototype. The graph plots **individual daily records at every date range**, never aggregated multi-day averages. Initially show 100 days of the available history. Horizontal swipes reveal more or less historical data; the time axis moves during gestures, while the graph redraws on release. The axis marks actual calendar months, switching to year markers for long spans. All bands use the same date columns, ending on the **last completed calendar day**. Do not plot today's still-incomplete values or allow them to change any band’s scale, including through the rolling Weight envelope. Current-day real values remain in the right-hand metric readouts; absent data remain unrecorded, not zero. The last graph date label shows its actual calendar date. The same rule applies to the selected historical recording date: its readouts show that day, but the plotted history ends the preceding day. There is no period selector.

Weight is shown using **actual weigh-in dots without white outlines** and a smooth filled high/low envelope derived from a seven-calendar-day window of genuine measurements, including context preceding the displayed period. Never invent missed weigh-ins. When the Weight target falls inside the existing visible weight-band scale, draw its coloured dashed target line like the other metrics, continuing the signed-in user’s current target through their visible earlier CSV history without adopting fictional CSV weight goals; **never expand the weight scale merely to display a distant target**. Calorie ranges and valid goals use the existing coloured dashed styling. **Do not show any popup or tooltip when tapping a chart day**; retain swiping/zooming, and revisit day interaction later. Preserve the currently approved band geometry and graph treatment unless a change is specifically requested.

Both portrait and landscape use the **same upright, left-to-right chart**, scaled to fit. Users can hide/show individual bands with explicit eye controls and reorder them by long-pressing and dragging their right-hand labels. A plain label tap must not accidentally change visibility. The installed PWA should request fullscreen without locking orientation.

## 3. Recording and daily history

- **Weight:** Double-tap its chart label to open the existing spacious entry sheet. Weigh-ins are stored as separate owner-private timestamped Firestore events with their local calendar date; the last actual weigh-in on a date determines that date’s chart value. Today's recorded weight appears immediately in its label, but is excluded from the graph and its scale until the following day. The daily graph never invents weigh-ins. Historical correction/deletion is still required. A single horizontal, speed-sensitive ruler starts from the previous measurement; slow swipes allow fine movement and the selected reading **snaps to 0.05 kg increments** (matching the scales), while fast swipes still cover more ground with momentum. Preserve all existing ruler markings and drawing geometry. The fixed full reading sits directly beneath the pointer. The screen has **Record** and **Cancel** only. Preserve irregular weigh-in history and allow corrections/deletions.
- **Water:** Water is an ordinary shared Food Item named exactly **Water** (normally per 100 mL). Every Food Item may explicitly contribute towards the water total via an optional **Counts towards water intake** control in the Food Item review/editor immediately below **Scan nutrition panel**. Off by default (zero water), except Water defaults to 100% for existing items without the setting and for newly named Water. When enabled, the user chooses **0–100% of the remaining 100 g/100 mL after subtracting protein, fat, carbohydrate, and fibre**, treated as an approximate water-mL contribution per 100 g/mL (1 g/mL density assumption for volume units). Avoid subtracting fibre twice where the source reports total carbohydrate inclusive of fibre (notably USDA). Clamp negative remaining mass to zero. Ordinary solid foods do not silently count towards water. The existing five recent amounts and New amount interface remains; shortcut drinks record a `foodEntries` snapshot for Water using its configured contribution, not always the full input volume. When any Food Item is included in a Dish or Meal, its water amount contributes proportionally, even through nested recipes and scaling, without double counting. Older standalone `waterEntries` remain counted for backwards compatibility. Water must exist in the shared library for the shortcut. Recent choices do not mix users.
- **Interaction:** A chart-label double-tap opens one intended entry sheet; neither tap may activate an action within the newly opened sheet.
- **Food and diary:** Every saved Food Item, Dish, and Meal editor has **Record serving at the top**. Record with a positive quantity and a base, whole, or familiar unit, preserving a nutrient and Water snapshot in owner-private `foodEntries`. After recording, return to the **Food Library search**, not the specific item/recipe. Double-tapping Calories, Fibre, Protein, Fats, or Carbs opens a chronological list of **food servings already recorded for the viewed date**, including each item's name and quantity/unit. Provide **Search** and **Scan barcode** to add food. Selecting an existing diary entry opens editing of its quantity and date, with original nutrition and Water values scaled proportionately rather than re-reading an updated shared food definition. Only entries belonging to the signed-in user are editable. The selected date (today by default) determines which date new servings are recorded against.
- **Activity log:** Double-tap the **Steps** label to open an owner-private Activity log (the Steps chart still has **no manual step entry**). Record an actual date, activity type, whole-minute duration, and Light/Moderate/Vigorous effort, with editing and deleting of previous records. Do not request calories burned, planned exercise, a goal date, or a manual step count. The app chooses an approximate MET value from an activity-and-effort table informed by the **2024 Adult Compendium of Physical Activities**. Include Walking, Running, Cycling, Swimming, Weights, Gardening, Housework, Hiking, Yoga, Sport, and Other. The form has a user-adjustable checkbox indicating whether the activity's steps will overlap with automatic step counts; walking, running, and hiking default to checked. For these three step-based activities, estimate the overlapping step count from duration and effort using explicitly provisional cadence assumptions; other checked activities use a conservative unknown-step overlap. Record multiple activities per day and allow backdating. Keep records isolated per account and synced offline through the pre-authorised `exerciseEntries` Firestore collection. Favourite/recent activity shortcuts remain future work.
- **Exercise graph markers:** Show a **small, hollow, warm coral circle close to the foot of the Steps band** on each completed day containing one or more actual private exercise records. This is a quiet activity indicator, not a drawn exercise duration/effort bar or another step column. It must not hide the step plumes or target line. Aggregate multiple activities on the day into one marker. The selected recording date is not plotted, consistently with the graph’s completed-day rule. Do not add chart-day popups.
- **Historical date mode:** A simple line-drawn **binoculars** button immediately left of the Settings cog opens a date selector, initially today. When a past date is selected, the app uses a visibly different, subdued background tone and clearly indicates the viewed date. Metric readouts, food diary, and new Weight, Water, Food, and Activity entries operate on that date. In the Activity log, the date defaults to the selected day. Return to Today exits historical mode. The graph shows only days preceding the selected date, and the historical Weight readout never uses future weigh-ins. Data for other dates and accounts remain untouched. **The diary** is a straightforward list without compulsory meal-time categories. Historical entries can be corrected.

**Personal details and targets:** Settings → **Details & Targets** contains optional Date of birth, Height (cm), and Sex (for resting-energy equations), followed by the five optional Weight (kg), Water (litres), Steps, Protein (g), and Fibre (g) targets. **Goal intensity**, immediately beneath Weight, is Gentle, Moderate (default), or Strong; it controls the intended *pace* of progress towards the weight goal, not the breadth of the recommended calorie range. Keep range width conceptually independent; do not add a separate range-width setting yet. Details and targets are saved together in the signed-in account's existing private `users/{uid}/settings/targets` Firestore document and synchronised across only that user's devices. Blank personal details or targets remain unset, without adopting fictional CSV goals. Editing is disabled until existing settings load, protecting offline, uninitialised data. Save returns to Settings; Back discards changes. Keep the existing Weight actual ÷ target convention. No assumed fat/carbohydrate targets or manual calorie-budget override. Do not require a usual-activity-level selection: step counts provide an activity indicator, while recorded exercise must account for other activities without double-counting steps. The Calories band now shows a provisional calculated daily range when a private weigh-in, date of birth, height, sex, and target weight are available; see section 6.

Steps must be obtained automatically from a compatible Android source (planned Health Connect), with **no manual step-entry screen** and no accessory requirement.

## 4. Approved food library

The approved library contains **only food records individually reviewed and explicitly approved by the users**. It must never be prepopulated with generic sample foods or bulk imports from nutritional reference datasets. Historical temporary food snapshots are retired; do not seed the new shared library from them.

The Food Library screen contains **one shared typeahead component for food names or barcode numbers, a Scan button, and one results list inside the dialog’s single scrollable pane**, reused in the Dish/Meal ingredient picker. **Before a search**, display only favourite and recently saved/edited or personally recorded Food Items, Dishes, and Meals, plus the Make a Dish and Put together a Meal actions; do not show the entire library. After saving any Food Item, Dish, or Meal from the library, clear its search and refocus the search input for the next lookup. Exception: saving a new ingredient from within an unfinished recipe returns to that recipe, preserving its draft and quantities. Searching does not change the form scale: the input is at least 16 px and does not acquire an extra external focus outline. Do not add explanatory paragraphs, provider sections, separate result headings, cards, or additional action panels. Display matching library items first, with **Food Item, Dish, or Meal** type badges only; never call those items “approved” anywhere in the interface. External suggestions have visibly lighter name text and are marked by source (NZ, Australian, USDA, barcode), indicating they are not yet part of the library. A manual “Add new Food Item” row appears once a search begins, immediately below library matches and above every external source result. Result rows must fit on-screen, **scrolling without a visible scrollbar or a reserved scrollbar gutter, while keeping item-type tags fully visible**. Do not solve this by unnecessary text wrapping or wasting the gap between name and tag. The barcode scanner preview sits at the **top** of the Food Library card while active. Use distinct Food Item/Dish/Meal badge colours from the chart (green, orange, purple). Make a Dish and Put together a Meal actions remain at the end of the list. Prepopulate manual creation from the typed name or barcode; do not show this row before searching. Search results and stored Food Item, Dish, and Meal names use **Capital Case**, never full capitals or arbitrary source casing. On all modal forms, focusing a populated text or numeric field selects its contents for immediate replacement. Numeric fields support upward/downward finger dragging with input-appropriate increments and acceleration (up increases; down decreases), without replacing the existing weight ruler. All modal screens (Settings, Account, Targets, food search, Food Item review, and Dish/Meal editing) must remain navigable with an on-screen keyboard. The dialog must resize to the actual visible viewport and use one scrollable content area, with active inputs kept in view and the dialog title/close control accessible. The NZ Food Composition Database is the primary reference for ordinary foods. Bundle **read-only, locally searchable reference indexes** from the NZ Concise Food Composition Tables 14th edition (2021, **1,278** distinct per-100 g records), Australian Food Composition Database Release 3 (**1,588**, including per-100 mL liquids), and USDA Foundation Foods October 2026 (**424**) in that order. All **3,290** records remain outside the approved library; users need not download or import them. Each source must remain visually identifiable and retain attribution, date, and original source references. The live NZ online database may be newer, but has no verified supported public search API.

For packaged foods, support typing or scanning barcodes and prefill name, brand, barcode, and straightforward pack-size conversions when available. Label any barcode data source (currently **only Open Food Facts** for live barcode lookup; NZ, Australian, and USDA bundled indexes are name-search references, not barcode providers). Prefer the English product name (`product_name_en`); if the source language is not English and an English name is missing, use a barcode placeholder and require manual name review rather than display an unverified foreign-language name. **Successful barcode identification does not guarantee correct nutrition**. Source values may be incomplete, outdated, or wrongly transcribed; provide editable nutrition fields and require checking and explicit approval. Potential alternatives remain research-only: FoodSwitch has NZ/Australian packaged-food data, but its API/licence is not verified for PieChart; USDA FoodData Central Branded Foods includes GTIN/UPC fields and an API key but is US-focused, so any future lookup must verify an exact GTIN match; FSANZ's Branded Food Database is not publicly accessible. GS1 data are not assumed to be a free public nutrition API. No reference or barcode source can populate the approved library automatically. Australian data attribution and licence notices must be maintained; USDA Foundation data are public domain. Preserve incomplete USDA nutrients as missing, never as implicit zero.

Selecting any external suggestion opens an editable review form. **Only an explicit “Add to library” save action** adds an external item to the shared library; this internal approval gate must not appear as an “approved” label in the interface. Product-label capture is a two-step option: scan a barcode to identify a packaged product, then use **Scan nutrition panel** on its review form to photograph or choose a label image. On-device OCR searches the photograph for **nutrient names first**; uses their positions to locate the panel and, where possible, rereads that region in table mode. It identifies the relevant **per-100 g/mL column by its heading and horizontal position**, then reads the intersections of nutrient rows with that column, regardless of nutrient order or intervening extra nutrients. If the heading is unclear but nutrient rows are recognisable, show the photograph and allow the user to tap the per-100 column. Never assume the last column or OCR text sequence is correct. It must not silently accept ambiguous values (e.g. an OCR `g` misread as a trailing `9`); unresolved values remain editable and require manual checking. The app never saves serving-column figures as per-100 values. The review form highlights values read from the photo, leaves unclear/missing fields for manual correction, and requires the user to verify the actual label before approving. The photo is not uploaded to any server or retained in the database; initial OCR model files may require an internet connection. Provide source information, allow manually entering a specific Food Item, and never silently populate the library or replace NZ name-search data with a different provider.

Every approved Food Item must have **energy, protein, carbohydrates, fats, and fibre**, normally per **100 g or 100 mL**. The review form is minimal and arranges nutrients **one per row in NZ food-label order**: energy, protein, fat, carbohydrate, and fibre. Energy has adjacent kJ and kcal inputs on the same row; each other nutrient has one numeric input with g units. Avoid explanatory per-field captions and clutter. Editing either energy field immediately updates the other using **1 kcal = 4.184 kJ**. Editing either energy input must immediately cross-calculate the other. Preserve legitimate small differences between both values printed on a manufacturer label; when external energy figures disagree materially (over 2%), use their kJ value to derive kcal unless the user explicitly corrects them. A missing calorie value is derived from kJ. Display **all nutrients and energy values with a maximum of two decimal places**, irrespective of source-database precision, and round approved nutritional values to at most two decimal places on save. Retain the unmodified external reference datasets; do not silently replace verified product-label figures or introduce explanatory field clutter. Missing figures require a reasonable, identified estimate rather than omission or an unlabelled zero. Store optional brand, barcode, original source, and per-value estimation/source status. Support editable, item-specific conversions for familiar units (slice, egg, cup, etc.); these are quantities of the same item, not separate database items. A familiar measure is **one named unit** with an explicit **g or mL per unit** amount (matching the item's per-100 base unit); the editor and dropdown must display the applicable unit and conversion. For example, slice = 35 g means 2 slices record 70 g of nutrition, while preserving the quantity as 2 slices. Existing stored labels such as "1 slice" remain compatible. Switching from base units to a familiar/whole unit resets the quantity to 1 (never inadvertently retain the default 100 as 100 slices); switching to the base unit defaults to 100. Offer previously used quantity/unit combinations in a later quick-entry refinement; that history is not yet implemented for food (the Water shortcut already has five recent quantities).

**Shared-library state:** Two Google accounts are authorised in the separate PieChart Firebase project, and the user verified that two Food Items created on the phone appeared on the computer. Start the shared approved library fresh. Earlier temporary approved-food snapshots are **retired** and are never automatically seeded or uploaded; existing old local copies, if any, are not deleted. The app may retain its prior device-local records without silently merging them into the authorised cloud library. Food Items, Dishes, and Meals remain shared; personal records and settings remain private to each member. Account → Copy food library produces a manual JSON export, **not** a recoverable backup. Approved Food Item changes affect future entries and recipes. A diary entry will retain a **small snapshot of its recorded nutritional values**; historic entries need not be recalculated for minor library corrections unless edited. Daily totals may be cached for efficiency.

## 5. Dishes and Meals

Three searchable, independently favouriteable levels: **Food Item → Dish → Meal**. Any level may be recorded directly. Dishes can contain Food Items or other Dishes; Meals can contain Food Items, Dishes, or other Meals. Prevent circular references.

The **Make a Dish** and **Put together a Meal** forms use the exact same reusable Food Library search component (not separate implementations), including library items, NZ/Australian/USDA source results, barcode lookup, and Add new Food Item. Selecting an external/manual item opens the standard editable review; saving it adds that ingredient to the current unfinished recipe while preserving its quantities and unsaved edits. Dishes and Meals add compatible components, add them with editable quantities and applicable units (g, mL, defined familiar measures, or a whole nested Dish/Meal), and save only deliberately named recipes into the approved library. Each saved recipe has a calculated total size and nutrition per 100 g (and for the whole recipe), derived from current ingredient nutrition. Treat the mass of measured liquids as approximate where density is unknown. Stored component IDs preserve relationships so later food and recipe edits update linked derived totals. Prevent deletion of ingredients still referenced by recipes. **Capital Case is required for all saved names, including imported foods, dishes, and meals.**

A saved Dish/Meal has defined ingredient quantities. Users can add, omit, scale, or explicitly substitute components; do **not** impose automatic substitution rules. Calculate total Dish weight from ingredient quantities. From an existing Dish or Meal, **Save as variation** opens a new recipe with the existing components but **a blank name**. The user must enter a name that is unique throughout the existing library; do not automatically append “Variation” or any other generated name. It is **linked to its parent by default**, inheriting parent components and future edits except for changed quantities, removed ingredients, or explicit additions; users can deliberately detach it into a standalone recipe. The link checkbox reads **Update details when [parent name] is updated**, accurately naming the parent recipe. Nested variations are supported. Dependency links are based on stable IDs and must reject circular references. Editing one recorded instance does not alter a shared template. New diary entries default to the saved recipe quantities, not the last recorded adjustment.

## 6. Calorie target and trends

**Primary output:** A daily **calorie-intake target range** to move towards the recorded weight goal without a deadline, shown in the Calories chart label and, on completed live days with a valid recorded weight, as the existing translucent chart-range band and coloured dashed bounds. Today’s intake is shown separately. The range is an *aim*, not a measure of nutrient sufficiency, a statistical confidence interval, or an exact energy measurement.

**v0.1.051 daily calculation (exercise-connected, steps pending; provisional):** The standalone pure-JavaScript engine in `calorie-budget.js` implements the **2023 National Academies adult (19+) Estimated Energy Requirement (EER) equations**, using the published *inactive* and *low-active* coefficients for age, sex-for-equation, height (cm), and most recently recorded **private** weight (kg). EER already includes resting metabolism, routine movement, and digestion; **do not add resting expenditure or a separate thermic-food allowance**. Use the private weight measured on or before the calculated date; never use public dummy-CSV weights for signed-in calorie recommendations. The app now has a **private activity/exercise log**, but **automatic step capture is not yet connected**, so the estimate remains provisional. The signed-in graph alone must not use fictional sample steps to set personalised calorie budgets.

**Goal-intensity interpretation (application choices, not validated personal weight-loss rates):** For *loss*, Gentle aims **5–10%**, Moderate **10–15%**, and Strong **15–20%** below estimated maintenance; for *gain*, Gentle **2–5%**, Moderate **5–8%**, and Strong **8–11%** above maintenance; at the target, maintenance flexibility is **±2.5%**. Intensity shifts the adjustment; the range width is independently expanded by unknown/variable actual activity. No goal date and no invented linear kcal/kg taper. If at least three private weigh-ins exist within the preceding 14 calendar days, the median determines whether the weight is within **0.25 kg** of goal; otherwise use the latest genuine private weight. The weight in the daily EER calculation remains the latest genuine private weight. Never create missed weigh-ins.

**Activity integration contract (manual exercise persistence and web step bridge implemented; companion device verification pending):** The engine accepts `stepDays: [{date:'YYYY-MM-DD', steps:<nonnegative integer>, complete:<boolean>}]` and `activities: [{date, minutes, mets, stepOverlap:<boolean>, stepsIncluded:<nonnegative integer, optional>}]`. The chart adapter now reads actual owner-private **`state.activityDays`** from `users/{uid}/exerciseEntries` via a Firestore snapshot listener. Each record has `{id,date,type,minutes,intensity,mets,stepOverlap,stepsIncluded,createdAt,updatedAt}`. This feeds the calorie calculation and the Steps graph marker. `state.stepDays` is now loaded live from owner-private `users/{uid}/dailyTotals` through the Health Connect companion bridge; without valid synced records actual step days are unknown, not zero. The watcher ignores unrelated dailyTotal documents and accepts only explicit `source: health_connect` step totals. Real completed step days can establish the cutoff between sample history and account-private history. An activity with `stepOverlap:false` is independent of the recorded steps (e.g. cycling); `stepOverlap:true` is an activity that contributes to steps (e.g. running or walking) and subtracts the walking-equivalent step expenditure before adding its own net MET expenditure. If `stepsIncluded` is not available, use a conservative overlap estimate; if `stepOverlap` is unknown, omit that activity rather than silently double-count. Calculate **net** energy above resting from MET activities (approximately `(MET−1)×weight(kg)×minutes/60`), never gross MET expenditure on top of EER.

**Step energy, recent days, and range variation:** NASEM's inactive activity category already includes normal daily life, so do not add every step on top of it. For extra level walking, apply the ACSM net energy estimate **~0.0005 kcal/kg/metre**, using an approximate **stride 0.415 × height(m)**, only for steps **above 3,000/day**. The 3,000-step reference and stride fraction are heuristic approximations; steps do not uniquely identify speed, gradient, or individual expenditure. Look back **21 days** for up to **14 completed step-count days**, requiring **at least 3** for a reliable rolling distribution; use their 20th/50th/80th percentiles. As today's incomplete steps arrive, count actual steps already accumulated and use this distribution **only for the portion of the day not yet measured**. This is a calculation, **not an anticipated activity entry**. If current-day steps are marked complete, use them without extrapolation. With sparse partial step data, use a wider fallback; with **no private step data whatsoever**, show a conservative maintenance envelope from NASEM *inactive to low-active*, without claiming to know actual steps. Historical completed days use their own measurements, never later steps. **Yesterday's exercise is not added again today**; recent *step* days inform typical unrecorded steps and their variation. Prior manually recorded exercise is preserved for its own day, not projected or double-counted into today's maintenance; estimating the probable remaining exercise from an incomplete log is not implemented. A daily calorie range is formed from the lower and upper plausible maintenance estimates and the selected intensity-band edges; range width therefore changes with today's observations and the spread of the previous completed days. This is **not a statistical confidence interval**. Round bounds **outwards to 25 kcal** without clipping either end.

**Clinical/technical limits:** The automatic estimator is for adults **19–110** with the required personal fields, not pregnant/breastfeeding people or other circumstances requiring personalised nutritional advice (the app does not yet screen for these). Do not recommend a loss goal with current or target BMI below **18.5**. Do not provide an underweight maintenance target automatically. If the lower calorie bound is below **1,200 kcal/day**, suppress the entire recommendation and request review rather than silently raise the range. That threshold is a conservative triage rule informed by NICE low-energy-diet guidance; **it does not establish nutritional adequacy or individual safety**. Never infer a missing weight, sex coefficient, activity log, or complete food diary from the sample data. The engine does not predict a date of goal achievement. It **does not yet calibrate itself** from intake/weight changes, because recording completeness is unknown; later calibration must use sustained trends and validated dynamic-energy approaches, not a fixed kcal/kg assumption.

**References:** [2024 Adult Compendium of Physical Activities](https://pacompendium.com/adult-compendium/) (MET estimates, not person-specific measurements); [Health Canada, published NASEM 2023 adult EER coefficients](https://www.canada.ca/en/health-canada/services/food-nutrition/healthy-eating/dietary-reference-intakes/tables/equations-estimate-energy-requirement.html); [National Academies, Adult PAL activity examples and limitations (2023)](https://www.ncbi.nlm.nih.gov/sites/books/NBK591020/); [ACSM walking metabolic equation](https://pmc.ncbi.nlm.nih.gov/articles/PMC7896743/); [2025 NICE weight management guidance](https://www.nice.org.uk/guidance/ng246/chapter/Physical-activity-and-diet); [NIH Body Weight Planner](https://www.niddk.nih.gov/health-information/weight-management/body-weight-planner) (dynamic model reference, **not claimed to be implemented**).

**Sample data:** In signed-in mode, sample CSV budgets appear only as historical sample values before the first real recorded entry, never as today's actual targets. The public CSV contains **114 user-supplied historical weigh-ins from 13 February–16 November 2026**; its other columns remain fictional. Do not import these weights automatically into another account or use them as private calculator measurements. Blank dates remain blank, never interpolated.


## 7. Accounts, storage, and delivery

Use **Google sign-in and Firebase** with separate private personal records for the two users and a shared approved Food Item/Dish/Meal library. Firestore access is limited to **two manually provisioned member UIDs** (no self-enrolment); the Firestore rules make all personal subcollections accessible only to their owner. Shared approved-food changes use real-time listeners and persistent offline caching. Use Google popup login while hosted on GitHub Pages, with a clear signed-in/connected/cached/unauthorised state. Unconfigured or signed-out prototype editing stays local; local records must not be conflated with a signed-in user's records. Entries must work offline and sync when connected, without losing unsynced records. Provide export and **automatic recoverable off-device historical backups**, separate from normal live synchronisation, with almost no ongoing administration. Firestore native managed backups require billing: **no automatic-backup approach is yet agreed or implemented**. Validate a safe no-cost alternative before production use.

Keep the GitHub Pages build lightweight, with vanilla HTML/CSS/JavaScript and a manifest. After the first complete deployment, distribute updates as **patch ZIPs containing changed files only**; unchanged files remain in the existing GitHub Pages repository. Later, package as a signed Android app where necessary for automatic steps; test Health Connect on the intended Xiaomi phones **early**, not after the rest of development. Preserve device and account security and minimise permissions.

**Settings organisation:** The Settings screen contains only three links, in order: **Food library**, **Details & Targets**, and **Account**. Account holds Google sign-in/out, connection status, identity, and the manual food-library copy/export, plus reference-data attribution. The Settings screen has no demo-graph CSV upload, reset, or other sample-data controls. Developers manage `dummy-data.csv` outside the app. Any previously stored local CSV override is ignored. All real account records and shared foods are unaffected.

**Personal goal graph lines:** In signed-in mode, any displayed CSV history must use the current account's optional Weight, Water, Steps, Protein, and Fibre goals, **never fictional CSV target values**. This prevents sudden target-line jumps at the last sample day/first real day. The underlying sample intake values are unchanged.

## Android steps companion — integration contract (v0.1.055 web, v0.2.000 Android)

The separate clean-rebuilt Android project **PieChartCompanion v0.2.000** is the native Health Connect bridge. It has been **compiled, signed, and installed successfully on the Xiaomi 13 Pro**. Each authorised user logs into the **same Firebase project** with their already-authorised Google account, grants READ_STEPS and optionally background health-data reading, and the companion aggregates Health Connect steps, never raw step records. The first supported route is Android 14+ with Health Connect and on-device tracking support; the native sensor fallback remains a separate future decision only if a phone cannot produce counts. The companion must not need Huawei Health.

Per-user data goes to **`users/{uid}/dailyTotals/{YYYY-MM-DD}`**, merged without erasing other fields. Step fields: `{date,steps,complete,source:'health_connect',syncedAt: serverTimestamp(),timeZone}`. Today is incomplete; prior local calendar days are complete. Health Connect's aggregated source deduplicates contributions; preserve only ONE total per day, do not sum multiple devices. Unavailable/denied or absent step data is not saved as zero. One owner-only web listener (`piechart-db.js`) reads these documents into `state.stepDays`, preserving the existing graph and `calorie-budget.js` adapter and no new Firebase rules. Date boundaries use each phone's local timezone; the current design assumes each account's phone remains in one primary time zone; travel/time-zone reconciliation needs real-world testing.

The companion performs a foreground on-demand sync and can optionally sync in the background when Health Connect supports and grants background reading; Android/Xiaomi battery optimisation can delay it. It requests the smallest needed permissions and can be signed out. It must not overwrite steps when permissions are missing or when Health Connect returns no data. Sync only a recent history period (last 21 completed days + today); no fitness data outside steps is collected. The signed APK was built through GitHub Actions after Android API, Kotlin compiler, JVM DSL, and signing-secret fixes. On the Xiaomi, the user signed in, granted Health Connect Steps access, and verified that manual companion synchronisation made step totals match in PieChart via Firebase. Initially Health Connect contained only a handful of recorded steps; it had just begun collecting data. Background step synchronisation, historic source completeness, and the Redmi remain unverified.
