# PieChart Companion — Current Specification

**Development rule:** Read this specification before every change and apply it alongside new user requirements. Update the relevant current-state requirements afterwards; replace superseded instructions rather than appending a release diary. Keep this document concise, accurate, and contradiction-free. Do not modify the PieChart PWA without separately checking its own specification. Subsequent code delivery is by timestamped **delta ZIPs containing only changed files**.

## Purpose and architecture

`nz.piechart.companion` is a small, optional Android 14+ companion to the GitHub Pages PieChart PWA. Firebase project: `julesvernespiechart`. The companion has two independent responsibilities: (1) synchronise Health Connect daily step counts to the user's private PieChart account; (2) scan nutritional panels locally using ML Kit (experimental), eventually as a dedicated scanner screen launched from PieChart's existing Food Item form. The scanner must never interfere with step synchronisation. No desktop Android Studio installation is expected; signed releases are built through the existing private GitHub Actions workflow. No paid services, cloud OCR, or scan upload.

## Steps — active and phone-tested

Google Credential Manager and Firebase Authentication sign in the owner. Before writing steps, verify `members/{uid}.active=true` using Firestore's server. Only write `users/{uid}/dailyTotals/{YYYY-MM-DD}` using merge semantics, with `date`, `steps`, `source=health_connect`, `complete` (false today), `timeZone`, and server `syncedAt`. Never change other fields, treat missing data as zero, or upload raw sensor/health data. Sync today and 21 preceding days manually; WorkManager background sync of today/yesterday is optional, governed by independent Health Connect background-read permission and Android scheduling. A phone-side sensor fallback is not included. The user reports working automatic sync on a Xiaomi 13 Pro with satisfactory battery consumption. Second-phone testing is outstanding. Preserve this existing functionality and its Firestore rules.

## Nutrition scanner — experimental reconstructed-label ML Kit and tested Stage 1 handoff

Use a **bundled, free, fully on-device Google ML Kit Latin OCR model** with CameraX; no scan upload, no paid services. Camera permission is requested on entry, with a separate Android photo picker for saved label photographs. Keep the scanner completely independent of existing Health Connect sign-in, permissions, and step-sync code. The companion's **Test nutrition panel scanner** button opens this experimental screen. Stage 1 app-to-app launch/return has been confirmed on the owner's phone using five fixed dummy readings; the independent live ML Kit scanner is not yet part of that handoff.

The live rear camera starts at **fixed 2× zoom**, clamped to the supported range, with no zoom controls. Allow tap-to-focus and show a scale warning **only when actual nutrient text in ML Kit's analysis image is too small**; large bounding-box heights by themselves are not evidence the camera must move away. Aim for sharply focused, comfortably framed labels. The per-100 column must be positively identified; do not accept per-serving values, and never silently infer a missing per-100 value.

**Current experimental scanner interface:** Show a large, persistent, translucent interpretation **over the live image**, with only the five required nutrient names (energy `#eb9920`, protein `#64b632`, fat `#ed5983`, carbohydrate `#269cf1`, fibre `#9c75bd`), a verified per-100 heading (energy colour), and candidate per-100 nutrient values highlighted. Keep recognised text readable, and identify tentative (`?`) versus confirmed (`✓`) values. Any individual nutrient can be tapped to reject its reading and request fresh OCR, without disturbing the other confirmed fields. The overlay can be collapsed to uncover the camera; screenshots are saved manually to Pictures/PieChart, with optional Debug and Android navigation-bar clearance. Never highlight irrelevant packaging text or all OCR words.

**General-purpose geometric interpretation (experimental):** Interpret each visible frame independently, including OCR boxes for named target rows, intermediate rows (e.g., saturated fat, sugars), and the positively verified per-100 g/mL heading. **For rows visible in the current frame, use direct same-row grouping as the primary value association**; mapped/estimated positions from other frames must not override these observed row relationships. First establish a meaningful nutrient-name anchor. Build a map of **measured positions relative to recognised reference rows**, then register overlapping views using at least two shared named anchors; reject uncertain geometric fits rather than guessing. Image tracking can help connect frames but failure must not block same-frame recognition. **Independently count the observed table rows**, including intermediate rows, and compare the candidate value's ordinal position with its nutrient-name row. Row counting is *not* a fixed assumed table order: it measures each unfamiliar label's actual rows. Apply this cross-check when the observed name and number sequences are complete enough; if incomplete, report row-order verification as unavailable rather than guessing. A demonstrated disagreement must block accepting the candidate. Values from distinct overlapping camera views can be shown only as tentative hypotheses if independently validated registration ties their coordinates to the same named row and verified per-100 column. **Do not lock a map-only hypothesis without a verified direct row association.** A missing or unclear target-row value must remain unresolved; never borrow a nearby intermediate-row value (e.g. gluten, saturated fat, sugars, or trans fat).

Maintain distinct provisional candidates, OCR/text consistency, geometric alignment, and row-count evidence. Multiple independently changed views corroborate the numeric text, decimal position, units, and correct row/column. Identical frames do not add independent evidence. Check dangerous decimal conflicts (e.g., `1.2` vs `12`) and gross macronutrient contradictions without synthesising replacement numbers. **Once a measurement has been confirmed it stays locked until the user explicitly taps that nutrient to rescan**; later OCR fluctuations, movement, or tracking loss must not overwrite or remove it. Rescan must not disturb other nutrients. When row-count evidence is unavailable, require stronger independently changed views of the same directly associated row before locking; row-count disagreement always vetoes a candidate. Counting must include observed intermediate rows and must never infer a missing row from a fixed template. Never use a serving value as a fallback, and never accept values when the per-100 heading is not verified. This is an experimental interpreter, not yet calibrated on all real label layouts; leave ambiguity provisional or Not found.

The **Test nutrition panel scanner** entry is still experimental, separate from the phone-tested five-dummy-values scanner handoff. It provides **Finish scan** (freeze the preview) and **Scan again**, a photo picker, voluntary **Copy OCR text**, and manual **Screenshot** saving only to local Pictures/PieChart for user feedback. A picked photo uses the existing one-shot parser rather than the live progressive camera reader. The current reconstruction is a preview only: there is no production per-nutrient confirmation screen yet, and final live OCR results are NOT sent to PieChart. Later, **Finish scan → review → individual nutrient rescans → Done** must happen in the companion. No companion-side typing or nutritional calculations. Images and OCR are never uploaded.

The companion **only recognises the explicitly labelled per-100 g or per-100 mL nutritional column** and five required fields: **energy, protein, total fat, carbohydrate, fibre**. Ignore per-serving values entirely, even when identical to per-100 values; never look for serving size on the label. The heading must be verified before accepting any nutrient. For the standalone photo/legacy parser, the previous same-frame left/right column constraint applies. For the live reconstruction prototype, the per-100 heading and numbers can be seen in different overlapping frames, **only if their geometric alignment to one reconstructed table is trustworthy**. If the heading was never established, or registration was lost, decline rather than substitute serving data.

Use **progressive accumulation across camera frames**: each frame may show just part of the label; retain raw readings until the user finishes. Allow competing OCR candidates and refuse to finalise when evidence is ambiguous, especially decimal/zero conflicts (`1.0` vs `10`). Repeated OCR is useful evidence but not proof; current reconstruction confidence logic needs further calibration and explicit conflict tests before production. On Finish, display the best consolidated raw numeric text and printed units (e.g., `1464 kJ`, `1.0 g`, `0 g`) for each nutrient, or **Not found** if missing or insufficiently confident. If no per-100 heading was established, report **Not found for all five**. No companion-side correction/editing interface. No conversion of kJ/kcal, nutrient estimation, serving-size inference, or nutritional calculations; all such work and all user corrections belong in PieChart's existing Food Item editor.

**Agreed production integration, not yet implemented:** The installed Android companion is launched directly by **Scan nutrition panel** in PieChart's existing Food Item editor, bypassing the companion's step-sync home screen. The scanner shows progressive readings, then **Finish scan → review → prompted individual nutrient rescanning as needed → Done**. Only **Done** returns the final five readings (original printed text/unit or explicit **Not found**, plus verified per-100 g/mL basis) to the **same unsaved PWA Food Item form**. PieChart handles the manual corrections, conversions, validation, and saving. The companion is not a second Food Item editor and must not save a food item or upload scanned content. Cancelling or using Android Back leaves PieChart's draft unchanged.

Stage 1 supplies a **temporary, phone-tested, test-only** exported `piechart-companion://scan` Activity, reachable from PieChart by Android intent. It presents two buttons: return five explicitly labelled fixed dummy values (1464 kJ, 6.0 g protein, 1.0 g fat, 81.0 g carbohydrate, 2.0 g fibre, per 100 g), or cancel with no change. It does not open the camera. Its HTTPS return URI is restricted to the owner-scoped `chlockasync.github.io` host and an `/index.html` path, pending confirmation of PieChart's actual deployed host; request/session ID must be present. No production OCR data is returned yet. **The user phone-tested Stage 1 successfully**: PieChart v0.1.079 returns to the same unsaved Food Item editor with its draft retained and five dummy readings populated (v0.1.078 had returned only to Today's Food). Real OCR results are not connected to the handoff.

For the production bridge, continue to enforce a deliberately scoped Android app-link/deep-link request-and-return protocol. Tie the response to its initiating scan session, allow only a trusted PieChart return destination, avoid retaining images/OCR in cloud storage, and handle missing companion, interrupted scans, repeat callbacks, and Android reopening the PWA in a new window. The **main PWA** is responsible for preserving/restoring the entire draft; the companion returns only scanner results and status. The dummy-value bridge has passed one full phone round trip; cancellation, app restart, repeated callbacks, and other-device variations still need testing. Keep the PWA's existing photo/Tesseract reader unchanged; longer-term non-Android fallback is undecided.

**Appearance:** The scanner is currently a native Android screen, not a dynamic display of PieChart's HTML/CSS. Its production screen must be deliberately styled to match PieChart's agreed Food Item UI (colours, typography, spacing, buttons, and review presentation), without changing Health Connect settings screens or assuming PWA styles update it automatically. Confirm the scanner's layout against the main app before final styling; unrelated PieChart pages do not need to be finalised first.

Regression example: the supplied glutinous rice flour label reads **per 100 g:** energy `1464 kJ`, protein `6.0 g`, total fat `1.0 g`, carbohydrate **printed** `0 g`, and fibre **not listed**. Per-serving `292.8 kJ` must not be substituted. Synthetic word/column tests cover raw values and missing fields. Previous phone testing found occasional OCR failures for zeroes and decimal points; report uncertainty rather than silently substituting guesses.

## Security, releases, and remaining validation

Android sandbox and HTTPS only, with Android backups and cleartext disabled. Permissions: INTERNET; read-only Health Connect steps and optional background-read; CAMERA for explicitly launched panel scanning. No GPS, contacts, microphone, SMS, broad media access, activity recognition, accessibility, or admin permission. Scanner image and OCR results must not enter Firestore. Credentials/signing material must never be committed or delivered in source patches. Keep manual private GitHub Actions signing in a separate job step after unsigned build and unit tests, with signed APK certificate verification. Changes must keep the same package ID and existing signing key so installed updates retain step-sync settings and Firebase sign-in.

**Latest phone findings and validation:** Six user-provided nutrition panels showed mixed results: several correct per-100 readings, missing heading/row matches on others, and dangerous missing decimal points (e.g. `7.4` recognised as `74`). The goal is accurate identification on unfamiliar layouts, not label-specific templates. User phone-tested v0.2.011 and identified a regression: fewer values recognised and incorrect intermediate-row values (including 0 g from a gluten/trans row) were attached and locked to Fat and Carbohydrate. **Current v0.2.012 repair** restores v0.2.010-style same-frame row grouping as the first source of matching evidence, preserving separate geometric registration and independent row counting only as supplementary evidence. Map-only values stay provisional and cannot lock. Tests must prove that intermediate-row values cannot be assigned to the wrong nutrient, that missing values never fall back to serving, and that accepted values survive later OCR noise. Android build and phone validation of the repair are outstanding. The established PWA handoff still returns dummy values, not live OCR. GitHub Actions must visibly build v0.2.012 (Android versionCode 212) with dated NZ-time, run-numbered APK/ZIP names, and an in-app version/build ID. The user's separate observation of duplicate **PieChart browser tabs** on callback remains unresolved; do not confuse these with installed APK instances. Preserve working Health Connect sync and Firebase configuration. No Firebase rule changes.
